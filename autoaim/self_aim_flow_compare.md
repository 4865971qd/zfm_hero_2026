# 自瞄流程与可用方法对照

本文按五层划分：观测层、建模层、预测层、决策层、诊断层。  
目标不是复述每个仓库的目录，而是提炼可复用的方法，并标出各项目更偏好的实现。

## 1. 总体共识

四个项目的主线其实一致：

1. 识别装甲板/目标
2. 由单板观测恢复位姿
3. 将单板观测归并成整车模型
4. 预测下一帧位置与相位
5. 选择击打板并计算开火时机
6. 用日志/曲线验证每一层

差异主要不在“有没有这些环节”，而在：

- 观测空间用 XYZ 还是更偏 RPD/YPD
- 车辆模型是规则驱动还是 EKF / 多候选打分
- 切板逻辑是“看到就切”还是“残差确认后切”
- debug 是简单输出还是分层状态消息

## 2. 观测层

### 可用方法

- 传统图像法：二值化、灯条提取、几何筛选、数字分类
- 深度学习法：YOLO/ONNX/TensorRT/NCNN/OpenVINO
- PnP 解算：从角点/框恢复单板位姿
- 时间同步：图像时间戳和 IMU/串口时间戳对齐

### 各项目特点

- `sp_vision_25-main`
  - 传统检测 + 多模型分类并存
  - 观测链路偏“工程整合”，适合离线测试和实车
  - 观测后直接进入 tracker/solver

- `dx_vision-main`
  - 检测、PnP、tracker、debug 消息拆得更细
  - 明显把“观测结果”和“候选位姿”区分开
  - 适合做状态可视化和后处理分析

- `wust_vision-main`
  - 检测后端很多：OpenCV / ONNX / TensorRT / NCNN / OpenVINO
  - 观测层更像“可插拔框架”
  - 适合做多平台部署，但复杂度也更高

- `autoaim`
  - 当前是“观测框 + PnP + tracker”的轻量链路
  - 强调日志和 PlotJuggler 可追踪性
  - 更适合你现在的实车调试节奏

## 3. 建模层

### 这一层解决什么

- 四块板是否属于同一辆车
- 哪两块板是同一组高度
- 当前相位是什么
- 圆心、半径、高度差如何维护

### 可用方法

- 规则板号匹配
- EKF 内部带相位状态
- 多相位候选打分
- 前哨站单独建模

### 各项目特点

- `sp_vision_25-main`
  - 普通目标和前哨站都有独立逻辑
  - tracker 中带有静止/切换/丢失等状态
  - 前哨站更偏规则驱动：相位、圆拟合、阶段确认

- `dx_vision-main`
  - 建模层最“状态化”
  - 直接维护 phase、pair、z1/z2、r1/r2 等状态
  - 对前哨站有更完整的分段更新思路

- `wust_vision-main`
  - 普通目标、前哨站、小陀螺、引导等任务分开
  - `armor_tracker`、`rune_tracker`、`guidance_tracker` 各自建模
  - 状态机味道更重，适合复杂任务拆分

- `autoaim`
  - 前哨站已经收敛成“看到就校正、看不到就外推、长时间看不到就重建”
  - 普通目标更多依赖稳定观测和板组归类
  - 你的当前风格更适合“简洁规则 + 日志验证”

## 4. 预测层

### 可用方法

- 线速度 / 角速度外推
- EKF 状态预测
- 观测缺失时保持模型
- 超时后销毁重建
- 快速收敛 / 加速更新

### 各项目特点

- `sp_vision_25-main`
  - EKF + 运动模型结合
  - 有静止模型、普通模型、前哨站模型
  - 适合工程上做“状态切换”

- `dx_vision-main`
  - 预测层更强，Q/R、NIS、加速窗口、相位切换都在里面
  - 对速度收敛和异常观测抑制更细
  - 适合复杂目标和高频调参

- `wust_vision-main`
  - 有多种 motion model：
    - `motion_model_crazy`
    - `motion_modelypdv2`
    - `motion_modelrypd`
  - 说明它更重视“模型族”而不是单一模型

- `autoaim`
  - 当前策略是轻模型：稳定观测时更新，短时丢观测时外推，长时间丢失时重建
  - 这和你的实车调试诉求是匹配的

## 5. 决策层

### 这一层解决什么

- 打哪块板
- 什么时候切板
- 什么时候提前切换
- 什么时候开火

### 可用方法

- 最近板优先
- 距离差 + 窗口保持
- 基于飞行时间的提前量补偿
- 边界阶段保守切换
- 满足稳定观测后再开火

### 各项目特点

- `sp_vision_25-main`
  - 更偏“规则 + planner”
  - 普通目标和前哨站都有相对独立的决策链
  - 适合比赛场景的工程化调参

- `dx_vision-main`
  - 决策层和 tracker 深度绑定
  - phase confirm、outpost mapping、velocity accelerate 都在这里影响结果
  - 优点是严谨，缺点是参数更密

- `wust_vision-main`
  - `auto_aim_fsm` 很明显：决策状态机化
  - 对多任务切换、不同模式适配更友好

- `autoaim`
  - 决策层是你当前最需要保留的“简洁版本”
  - 重点是“谁更近打谁”，再叠加切板保持和飞行时间补偿
  - 你的方向是对的，不必为了复杂而复杂

## 6. 诊断层

### 最有价值的 debug 字段

- 观测值：`obs_x/y/z`、`obs_yaw`、`matched`
- 模型值：`model_cx/cy/z`、`model_yaw`、`v_yaw`
- 残差：`res_x/y/z`、`res_yaw`、`res_norm`
- 选板：`sel_idx`、`sel_raw_idx`、`sel_margin`
- 时序：图像时间、IMU 时间、串口年龄、消息延迟

### 各项目特点

- `sp_vision_25-main`
  - PlotJuggler 很成熟，适合看曲线
  - 文档里就明确把它当调参工具

- `dx_vision-main`
  - debug 消息分层最清楚
  - 适合做 tracker phase、performance、estimate 的可视化

- `wust_vision-main`
  - 有 web/chart/json_view 这类前端工具
  - 更适合在线看状态，但调试门槛也高

- `autoaim`
  - 现在的方向最好：让可视化直接反映“观测框、选择框、击打框”
  - debug 不要替代算法，只服务于判断算法是否选对

## 7. 可以直接复用的结论

1. 观测层别把“识别结果”和“位姿结果”混成一个黑盒。
2. 建模层要明确“单板 -> 整车 -> 相位”这条归并链。
3. 预测层不要太重，先保证短时外推和长时重建。
4. 决策层重点是“谁打、何时打、是否提前切换”。
5. debug 层要能一眼看出是观测错、建模错、预测错，还是决策错。

## 8. 对你当前 autoaim 的建议

最适合你的不是最复杂的那种，而是：

- 观测：稳
- 建模：轻
- 预测：短时外推 + 超时重建
- 决策：最近板优先 + 保持
- 调试：PlotJuggler 看残差和选板

这套最贴合你实车日志，也最容易持续修正。
